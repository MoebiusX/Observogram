# Vendoring Observogram's libraries and upgrading the snapshot

A downstream distribution — a private build with its own backend access,
auth, branding or artefact taxonomy — runs a vendored snapshot of
Observogram's pure libraries plus a thin layer of its own. This document is
the workflow for that snapshot: **snapshot → verify hashes → run module smoke
tests → bump**. The contract it rests on is one generated file,
[`VENDOR-MANIFEST.json`](../VENDOR-MANIFEST.json).

[`VENDORING.md`](VENDORING.md) is the companion document for the studio-side
set (the verdict/diff engines, the design system) and the prose contracts
upstream keeps stable; the `tools/lib` rows of its table are a subset of the
manifest.

## 1. What the manifest is

`VENDOR-MANIFEST.json`, at the repository root, lists every module under
`tools/lib` a downstream may copy verbatim. It is generated by
`npm run vendor-manifest` (`tools/gen-vendor-manifest.mjs --write`), committed,
and guarded by `tools/test-vendor-manifest.mjs` in `npm test`: a stale
manifest fails the build with the one command that fixes it.

| Field | Meaning |
| --- | --- |
| `manifestVersion` | the shape of this file; `1` only gains keys |
| `package`, `version` | `package.json`'s name and version — the upstream release the snapshot belongs to (unreleased work accrues under the last released version) |
| `root` | `tools/lib` — every path below is relative to the repository root and lives under it |
| `modules[path].sha256`, `.bytes` | the raw bytes of the file as committed (`.gitattributes` forces LF for `*.mjs`) |
| `modules[path].exports` | the exported names, code-point sorted, read statically from the source and cross-checked against the real module namespace by the guard |
| `modules[path].imports` | the other listed modules it imports (relative specifiers resolved) — copy them together |
| `modules[path].npm` | the npm packages it needs (`@prometheus-io/lezer-promql` for `promql-lezer.mjs`; nothing else) |
| `modules[path].changedSinceRelease` | `true` when the module's exports differ from the ones released as `version`; then `releasedExports` carries the released list (`null` for a module new since the release) |
| `data[path]` | non-code files under the root (`tools/lib/site/inventory.schema.json`), sha256 and bytes |
| `excluded[path]` | the modules under `tools/lib` that are **not** vendorable, each with the reason |
| `removedSinceRelease` | modules that left the set since `version` |

It carries no timestamp: regenerating it on an unchanged tree is
byte-identical, so the diff between two snapshots is exactly what changed.

## 2. The inclusion rule

A module is listed when, mechanically:

1. it imports no `node:*` module, reads no `process`, touches no DOM or web
   storage (`document`, `window`, `navigator`, `localStorage`,
   `sessionStorage`), reads no `import.meta` and calls no `require()` — judged
   on code, never on comments or string text;
2. every relative import resolves to another listed module (the import graph
   stays inside the set) and every bare import is a declared
   `package.json` dependency;
3. its export forms are plain (`export const|let|var|function|class` and
   `export { … }` lists; `export default` and `export *` make generation fail
   so support is added deliberately);
4. it is not in `EXCLUDED` in `tools/gen-vendor-manifest.mjs`.

Every `.mjs` under `tools/lib` is listed or excluded, never neither — the
guard enforces the coverage. The exclusions, with the reasons the manifest
publishes:

| Module | Why it is out |
| --- | --- |
| `tools/lib/journey.mjs` | `node:fs/path/url`, an import-time schema read, imports of `studio/diagnostic-grade.mjs` and `studio/verify-deploy.mjs`, a dynamic import of `tools/fetch-live-pack.mjs` — the server-side journey runner, the documented browser-safety exception |
| `tools/lib/brand-env.mjs` | `node:fs/path` and `process.env` — server-side brand/env resolution |
| `tools/lib/grafana-mcp-bridge.mjs` | a `node:http` server and network calls — a bridge process |
| `tools/lib/harness.mjs` | `process.stdout` / `process.exit` — the repo's own test harness |
| `tools/lib/retrofeed.mjs` | pure by the rules, but it imports `studio/verify-deploy.mjs`, so its import graph leaves `tools/lib` |

`studio/metric-readers.mjs` and the other zero-import studio modules
`VENDORING.md` names are not under `tools/lib` and are not in this manifest
(see *Not covered*).

## 3. Snapshot

1. Pick the upstream tag or commit and record it next to your copy (a
   `UPSTREAM` file, a lockfile comment — anything you will read again).
2. Copy `VENDOR-MANIFEST.json` and `tools/gen-vendor-manifest.mjs` into your
   tree. The script imports node built-ins only and nothing from `tools/lib`,
   so it runs anywhere beside the manifest.
3. Copy the listed modules you need **with the modules their `imports` name**,
   preserving the `tools/lib/…` layout under one directory so the relative
   imports resolve. Copy the bytes verbatim: a tool that converts line
   endings produces files whose hashes differ (`--verify` says so).
4. Install the npm packages the `npm` fields name, at the versions upstream's
   `package.json` pins.

## 4. Verify hashes

```sh
node tools/gen-vendor-manifest.mjs --verify <vendored-root>
```

`<vendored-root>` is the directory that holds `VENDOR-MANIFEST.json` and the
`tools/lib/…` tree. Each listed module and data file prints `ok`, `drift`
(the bytes differ from the manifest — with a hint when only the line endings
do) or `missing`; the exit code is 1 on anything but `ok`. It never
regenerates anything.

A local patch is drift by definition. Keep patches as a separate overlay
applied after the copy, so `--verify` on the pristine copy stays clean and
the overlay is the list of what to re-apply at the next bump.

## 5. Run module smoke tests

```sh
node tools/gen-vendor-manifest.mjs --smoke <vendored-root>
```

Imports each listed module from your copy and compares its export names
with the manifest; a module whose dependency was not copied, or whose npm
package is not installed, fails here with the loader's error. For deeper
coverage copy the upstream unit test of a module and run it with
`node --test`:

## 6. Bump

1. Diff the old and the new `VENDOR-MANIFEST.json`. Per module, `exports`
   added or removed is an API change; `removedSinceRelease` and the
   `excluded` table list what left the set; a module whose `exports` are
   unchanged while its `sha256` moved is a behaviour update, not an API
   break. `changedSinceRelease` in the *new* manifest tells you what moved
   since its release; between two releases, read the release section of
   [`CHANGELOG.md`](CHANGELOG.md) for every module the diff names — upstream
   names each one there.
2. Re-copy the modules (step 3), re-apply your overlay, run `--verify` and
   `--smoke` (steps 4 and 5), then your own tests.
3. Record the new upstream tag or commit.

## 7. What upstream promises

- The exports of a listed module change only with a `## Unreleased` entry in
  `docs/CHANGELOG.md` that names the module (path or backticked basename);
  `tools/test-vendor-manifest.mjs` fails the build otherwise. The mention
  check is a text heuristic backed by review of the manifest diff in the
  pull request — it is the signal, the CHANGELOG entry is the notice.
- A module leaves the set only with a CHANGELOG entry naming it.
- Listed modules stay pure by the rule above; the guard asserts it on every
  run, and asserts the excluded ones still break a rule so the rule cannot
  go soft.
- The manifest shape (`manifestVersion: 1`) only gains keys.
- Static export extraction equals the real module namespace for every listed
  module (asserted on every run).

## 8. Not covered

- Server routes, studio views and the store: the manifest is the library
  contract, not an API contract.
- The zero-import studio modules `VENDORING.md` lists (`diagnostic-grade`,
  `artifact-model`, `constants`, `verify-deploy`, `metric-readers`): still the
  prose table, still CI-asserted zero-import; folding them into the manifest
  (which would also let `retrofeed.mjs` enter the set) is a follow-up.
- The other downstream seams — artefact taxonomy, branding, proxy identity,
  the embeddable studio bundle — are documented where they land; the
  *Decisions — downstream seams* section of
  [`UPDATE_JOURNEY.md`](UPDATE_JOURNEY.md) tracks them.

## 9. The private plugin layer

A downstream runs the vendored snapshot plus a thin layer of its own. Each
seam is configuration the snapshot reads, never a patch to it — so a bump is
a bump. The surface so far:

| Seam | Configuration | Where it is documented |
|---|---|---|
| Backend access (W2) | `OBSERVOGRAM_TRANSPORT_HOOK=<path.mjs \| file:URL>` — a module exporting `prepareRequest({ url, headers })` and/or `fetchImpl(url, init)`, applied to every MCP request of the CLI, the recorder, the probes, journeys and the studio server; `OBSERVOGRAM_ALLOW_LOCAL_MCP=0` still binds the URL it returns | [`MCP_INTEGRATION.md`](MCP_INTEGRATION.md), "Transport hook" |

A minimal plugin layer for the backend seam is one file the deployment
points at:

```bash
# hooks/gateway.mjs: export function prepareRequest({ url, headers }) { … }
OBSERVOGRAM_TRANSPORT_HOOK=/opt/observogram-plugins/hooks/gateway.mjs npm run dev
```

The client the hook plugs into, `tools/lib/mcp-client.mjs`, is itself a
listed module of this manifest: a downstream that vendors it gets the same
`transport` parameter (`createMcpClient({ mcpUrl, mcpAuth, timeoutMs,
transport })`) and the same `TransportHookError` contract in its own
tooling.
