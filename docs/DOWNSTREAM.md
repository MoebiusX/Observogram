# Vendoring Observogram's libraries and upgrading the snapshot

A downstream distribution — a private build with its own backend access,
auth, branding or artefact taxonomy — runs a vendored snapshot of
Observogram's pure libraries plus a thin layer of its own. This document is
the workflow for that snapshot: **snapshot → verify hashes → run module smoke
tests → bump**. The contract it rests on is one generated file,
[`VENDOR-MANIFEST.json`](../VENDOR-MANIFEST.json).

[`VENDORING.md`](VENDORING.md) is the companion document for the studio-side
set (the verdict/diff engines, the design system) and the prose contracts
upstream keeps stable; the `tools/lib` rows of its table are a subset of the
manifest.

A downstream that keeps the whole repository and runs it as its product
refreshes it with [`DOWNSTREAM_REFRESH.md`](DOWNSTREAM_REFRESH.md). The
manifest checks below are one of its steps.

## 1. What the manifest is

`VENDOR-MANIFEST.json`, at the repository root, lists every module under
`tools/lib` a downstream may copy verbatim. It is generated by
`npm run vendor-manifest` (`tools/gen-vendor-manifest.mjs --write`), committed,
and guarded by `tools/test-vendor-manifest.mjs` in `npm test`: a stale
manifest fails the build with the one command that fixes it.

| Field | Meaning |
| --- | --- |
| `manifestVersion` | the shape of this file; `1` only gains keys |
| `package`, `version` | `package.json`'s name and version — the upstream release the snapshot belongs to (unreleased work accrues under the last released version) |
| `root` | `tools/lib` — every path below is relative to the repository root and lives under it |
| `modules[path].sha256`, `.bytes` | the raw bytes of the file as committed (`.gitattributes` forces LF for `*.mjs`) |
| `modules[path].exports` | the exported names, code-point sorted, read statically from the source and cross-checked against the real module namespace by the guard |
| `modules[path].imports` | the other listed modules it imports (relative specifiers resolved) — copy them together |
| `modules[path].npm` | the npm packages it needs (`@prometheus-io/lezer-promql` for `promql-lezer.mjs`; nothing else) — the static bundle's builder reads it too: a bundle inlines the packages this field names for the modules it carries, and the packages those import (§10) |
| `modules[path].changedSinceRelease` | `true` when the module's exports differ from the ones released as `version`; then `releasedExports` carries the released list (`null` for a module new since the release) |
| `data[path]` | non-code files under the root (`tools/lib/site/inventory.schema.json`), sha256 and bytes |
| `excluded[path]` | the modules under `tools/lib` that are **not** vendorable, each with the reason |
| `removedSinceRelease` | modules that left the set since `version` |

It carries no timestamp: regenerating it on an unchanged tree is
byte-identical, so the diff between two snapshots is exactly what changed.

## 2. The inclusion rule

A module is listed when, mechanically:

1. it imports no `node:*` module, reads no `process` (but for exactly the
   two guarded forms `globalThis.process?.cpuUsage?.()` and
   `globalThis.process?.platform` — `PROCESS_READS_ALLOWED`: the CPU time and
   the platform `artefact-classify.mjs`'s id clocks read where the runtime has
   them; a browser reads `undefined`, and the wall clock decides), touches no
   DOM or web storage (`document`, `window`, `navigator`, `localStorage`,
   `sessionStorage`), reads no `import.meta` and calls no `require()` — judged
   on code, never on comments or string text;
2. every relative import resolves to another listed module (the import graph
   stays inside the set) and every bare import is a declared
   `package.json` dependency;
3. its export forms are plain (`export const|let|var|function|class` and
   `export { … }` lists; `export default` and `export *` make generation fail
   so support is added deliberately);
4. it is not in `EXCLUDED` in `tools/gen-vendor-manifest.mjs`.

Every `.mjs` under `tools/lib` is listed or excluded, never neither — the
guard enforces the coverage. The exclusions, with the reasons the manifest
publishes:

| Module | Why it is out |
| --- | --- |
| `tools/lib/journey.mjs` | `node:fs/path/url/util`, an import-time schema read, imports of `studio/diagnostic-grade.mjs` and `studio/verify-deploy.mjs`, a dynamic import of `tools/fetch-live-pack.mjs` — the server-side journey runner, the documented browser-safety exception |
| `tools/lib/brand-env.mjs` | `node:fs/path` and `process.env` — server-side brand/env resolution |
| `tools/lib/grafana-mcp-bridge.mjs` | a `node:http` server and network calls — a bridge process |
| `tools/lib/harness.mjs` | `process.stdout` / `process.exit` — the repo's own test harness |
| `tools/lib/retrofeed.mjs` | pure by the rules, but it imports `studio/verify-deploy.mjs`, so its import graph leaves `tools/lib` |

`studio/metric-readers.mjs` and the other zero-import studio modules
`VENDORING.md` names are not under `tools/lib` and are not in this manifest
(see *Not covered*).

## 3. Snapshot

1. Pick the upstream tag or commit and record it next to your copy (a
   `UPSTREAM` file, a lockfile comment — anything you will read again).
2. Copy `VENDOR-MANIFEST.json` and `tools/gen-vendor-manifest.mjs` into your
   tree. The script imports node built-ins only and nothing from `tools/lib`,
   so it runs anywhere beside the manifest.
3. Copy the listed modules you need **with the modules their `imports` name**,
   preserving the `tools/lib/…` layout under one directory so the relative
   imports resolve. Copy the bytes verbatim: a tool that converts line
   endings produces files whose hashes differ (`--verify` says so).
4. Install the npm packages the `npm` fields name, at the versions upstream's
   `package-lock.json` pins (a static bundle build refuses any other, §10).

## 4. Verify hashes

```sh
node tools/gen-vendor-manifest.mjs --verify <vendored-root>
```

`<vendored-root>` is the directory that holds `VENDOR-MANIFEST.json` and the
`tools/lib/…` tree. Each listed module and data file prints `ok`, `drift`
(the bytes differ from the manifest — with a hint when only the line endings
do) or `missing`; the exit code is 1 on anything but `ok`. It never
regenerates anything.

A local patch is drift by definition. Keep patches as a separate overlay
applied after the copy, so `--verify` on the pristine copy stays clean and
the overlay is the list of what to re-apply at the next bump. Where a patch
has to live inside the copy, mark every changed line
`// LOCAL DEVIATION (<org> <TAG>): <why>`: `--verify` then reports the file as
`drift (local patch (marked LOCAL DEVIATION) — re-apply it at the next bump,
or send it upstream)` instead of bare drift, so a reviewer can tell a known
patch from a copy that went wrong; markers that use other words are named
with `--patch-marker <text>` (plain text, case-sensitive, never recorded
here). A tree that vendors the whole repository
rather than the listed modules is refreshed by
[`DOWNSTREAM_REFRESH.md`](DOWNSTREAM_REFRESH.md): the copy is replaced from
`npm run vendor-export` (the commit's files minus `export-ignore`) and proven
byte for byte with its `--check` against the `VENDOR-TREE.json` the export
writes, and its local patches are one commit re-applied on top. Send upstream the patches that are engine concerns:
a merged patch stops being drift.

## 6. Bump

1. Diff the old and the new `VENDOR-MANIFEST.json`. Per module, `exports`
   added or removed is an API change; `removedSinceRelease` and the
   `excluded` table list what left the set; a module whose `exports` are
   unchanged while its `sha256` moved is a behaviour update, not an API
   break. `changedSinceRelease` in the *new* manifest tells you what moved
   since its release; between two releases, read the release section of
   [`CHANGELOG.md`](CHANGELOG.md) for every module the diff names — upstream
   names each one there.
2. Re-copy the modules (step 3), re-apply your overlay, run `--verify` and
   `--smoke` (steps 4 and 5), then your own tests.
3. Record the new upstream tag or commit.

## 7. What upstream promises

- The exports of a listed module change only with a `## Unreleased` entry in
  `docs/CHANGELOG.md` that names the module (path or backticked basename);
  `tools/test-vendor-manifest.mjs` fails the build otherwise. The mention
  check is a text heuristic backed by review of the manifest diff in the
  pull request — it is the signal, the CHANGELOG entry is the notice.
- A module leaves the set only with a CHANGELOG entry naming it.
- Listed modules stay pure by the rule above; the guard asserts it on every
  run, and asserts the excluded ones still break a rule so the rule cannot
  go soft.
- The manifest shape (`manifestVersion: 1`) only gains keys.
- Static export extraction equals the real module namespace for every listed
  module (asserted on every run).

## 8. Not covered

- Server routes, studio views and the store: the manifest is the library
  contract, not an API contract.
- The studio modules `VENDORING.md` lists (`diagnostic-grade`,
  `artifact-model`, `constants`, `verify-deploy`, `metric-readers`, and the
  Overview board's five files): still the prose table, still CI-asserted; folding them into the manifest
  (which would also let `retrofeed.mjs` enter the set) is a follow-up.
- The npm packages a static bundle carries beyond the `npm` fields' roots
  (`@lezer/lr`, `@lezer/highlight` and `@lezer/common`, which
  `@prometheus-io/lezer-promql` imports): the manifest names the roots; every
  package a build embeds is listed by the bundle itself — its licence block
  and the builder's `--json` `thirdParty` (§10).
- The other downstream seams are configuration the snapshot reads (§9: the
  transport hook, the taxonomy, the reverse-proxy identity, the brand; §10:
  the embeddable studio bundle); the *Decisions — downstream seams* section
  of [`UPDATE_JOURNEY.md`](UPDATE_JOURNEY.md) tracks them.
- Platform-specific behaviour beyond what [`PLATFORMS.md`](PLATFORMS.md) states: Windows as [`PLATFORMS.md`](PLATFORMS.md) says
  (tested in CI on `windows-latest`); macOS is untested (the POSIX suites run
  there, no CI leg).

## 10. Embedding the studio

A downstream that serves the studio from its own static host does not run the
Express server in front of it; it builds the studio from the vendored snapshot
as one file and serves that:

```bash
# From the snapshot (the whole tree, not only tools/lib — the bundle inlines studio/ too),
# with its package-lock.json, VENDOR-MANIFEST.json and LICENSE, installed from the lockfile:
npm ci
node tools/build-studio-bundle.mjs \
  --pack packs/orders.pack.yaml --id orders --label "Orders" --description "Order intake and fulfilment" \
  --pack-url https://packs.example.internal/payments.pack.yaml --label "Payments" \
  --taxonomy taxonomy.json --brand brand.json \
  --out dist/studio/index.html
```

Each pack takes its own `--id`, `--label` and `--description` — the catalogue
row the bundled studio shows. The file loads no font over the network: the
shell's three Google Fonts lines (two preconnects and the stylesheet) are
dropped, and the stylesheets' font stacks apply. `--remote-fonts` keeps them,
for readers who are online, and the page then asks `fonts.googleapis.com` and
`fonts.gstatic.com` for the fonts; `--no-remote-fonts`, the default, is still
accepted, and the two together are a usage error.

What is in the file: `studio/index.html` with every stylesheet inlined in
place, an inline import map whose keys are `studio/<file>.mjs` and
`lib/<path>.mjs` (for `tools/lib`) and whose addresses are `data:` URLs of each
module with only its import-specifier strings rewritten, the packs' canonical
manifests and the spec schema as a JSON block, and `studio/static-backend.mjs`
installed before `studio/app.mjs` boots. The shim is the route table of the
bundle — each handler is a port of the `server/index.mjs` handler it names,
over the same `tools/lib` engines, and `tools/test-studio-bundle.mjs` compares
every ported route (status, content type, body; the export ZIP's headers and
entry names) against a running server:

| Answered in the browser | Answered `501 { ok: false, denied: 'no-backend', error: '<Feature> needs the Observogram server; this studio is a static bundle built without one.' }` |
|---|---|
| `GET /api/packs`, `/api/packs/:id` (+ `?env=`), `/canonical` (JSON, `?format=yaml`), `/conformance`, `/compile-catalog`, `/compile-artifact`, `/compile/:target`, `/export.zip` (the Export button downloads it as a Blob); `/api/compile/targets`, `/api/maturity-rubric`, `/api/version`, `/healthz`, `/api/taxonomy` (unconfigured, or the document `--taxonomy` baked — a v2 file's `glossary` included, so the glossary marks draw as on a server), `/api/mcp-settings` (`proxy: false`; the policy `--mcp-settings-policy` baked or `null`, and `mcpOrigins` when `--mcp-origins` baked a list), `/api/examples` and `/api/references` (empty), `/api/live-status` (`present: false`); `/api/packs/:id/verdicts` (the empty document — a bundled pack is never registered, so this is the server's own answer); `/api/packs/:id/placeholders` (the placeholder report, the zero-store engine in the browser); `/auth/me` → `404 { ok: false, error: 'identity not configured' }` (the open posture); `GET /api/diff` (Compare: the diff and its traceability graph, computed in the browser over two packs the bundle carries — the PromQL parser and the packages it imports inlined from the lockfile); `POST /api/packs/:id/retrofeed` (retrofeed, the one non-GET answered: computed in the browser over two packs the bundle carries, written nowhere, with the server's body parsing and refusals — a `Content-Encoding`, a JSON body in a UTF charset other than UTF-8 and a text body's charset are not ported); `GET /api/packs/:id/audit-report` (the service audit report, JSON or HTML with the bundle's brand over its own design kit, its goes-blind section computed in the browser; a bundle has no store, so `assessments` and `waivers` are `available: false`, "not recorded by this build"; the generator is `<product> static bundle`, `pack.source` `bundle` or `url`; the Conformance view's download anchors are answered by the shim's click handler as a Blob download) | every other `/api` or `/auth` path and every non-GET but retrofeed: Scan a repo (`/api/crawl*`), Draft from MCP, Refresh from MCP, Testing an MCP connection (`/api/mcp/ping`), Building a pack from a live MCP server (`/api/mcp/jobs`), uploads (`/api/validate`, `/api/uploads`), Deploy, Journeys, Build (`/api/library*`), Verdicts (`PUT` / `DELETE …/verdicts/:artefact`), Waivers (`/api/waivers`, `/api/services/:id/waivers` — a bundled pack has no service record), Services (`/api/services`, `/api/services/:id` — the records behind the home's cards and the service page; a bundle has no services table, so the home lists the services its packs name), Organisations (`/api/orgs` — the active org's name and effective role), Settings (`/api/org`, `/api/org/members`, `/api/environments/:id`, `/api/mcp-endpoints`, `/api/repository-sources`, `/api/audit` — a bundle has no org, so Settings shows this sentence), Passing MCP server settings through the studio server (`/api/mcp-settings/describe`, `/submit` — the opt-in pass-through; the bundle's Server settings modal sends from the browser), sign-in (`/auth/*`) |

The bundle opens on the Expert home, never on Overview: the studio's front
door reads the services table and the journeys, and both answer 501 here. A
host that wants the board vendors it (VENDORING.md, *The Overview board*) and
feeds its model from its own records.

Swapping packs is a rebuild: `--pack` inlines a file validated against the
schema at build time; `--pack-url` names a URL the page fetches at its first
catalogue read (the host must answer CORS; a URL that fails is a catalogue
entry with `ok: false`, never a failed boot; a URL carrying userinfo or a
credential query parameter is refused, because the file is distributed).
Upgrading is a snapshot bump, an `npm ci` and a rebuild — the bundle has no
configuration of its own to migrate.

### Rebadge batch 2, B1: baking the taxonomy and the brand

The two seams a server reads from its environment (§9, W3 and W4) are baked
at build time, through the server's own code on both sides. `--taxonomy
<file.json>` is read, parsed and validated with `validateTaxonomy`
(`tools/lib/artefact-classify.mjs`) exactly as `server/taxonomy.mjs` does — a
bad file fails the build with `--taxonomy: <path>: <reason>`, the server's
texts — and the document is written into the bundle's config; the shim's
`GET /api/taxonomy` then answers `{ ok, taxonomy, configured: true }` with
`Cache-Control: no-store`, the server's shape, and the studio's boot binds it
as it binds a server's, so Discover groups a typed pack as a server started
with `OBSERVOGRAM_TAXONOMY` does. `--brand <file.json>` goes through
`tools/lib/brand-env.mjs loadBrand` — the server's one loader, so the
`OBSERVOGRAM_BRAND_*` scalars apply on top of the file as on a server — and
the shell is `brandShellHtml`'s rendering of `studio/index.html` (title,
description, header, footer, `#brand-config`, `#brand-tokens`, favicon)
before the stylesheets are inlined, so `#brand-tokens` lands after
`design-tokens.css` as on the server; the chrome, the notice and the `501`
texts read the product from `#brand-config`, and a branded bundle renders
the upstream name nowhere. When a flag is absent the server's variables are
honoured (`OBSERVOGRAM_TAXONOMY`, `OBSERVOGRAM_BRAND_FILE`, the scalars, the
legacy `TOMOGRAPH_` spelling): a build machine configured for a server bakes
what that server shows; build unbranded there by unsetting or emptying the
variable (an empty value counts as unset): `env -u OBSERVOGRAM_BRAND_FILE` in
a POSIX shell, `set OBSERVOGRAM_BRAND_FILE=` in cmd,
`$env:OBSERVOGRAM_BRAND_FILE=''` in PowerShell. Brand URLs must
not be server paths — `favicon`, `logo.url` and `hero.src` are an absolute
URL, a `data:` URL or a path relative to the bundle's own directory (resolved
against the page's URL by the static host; the builder copies no asset), and
`/assets/x` fails the build naming the field and the fix. The default brand's
Discover hero is the server asset `/assets/observogram-hero.png` in every
unbranded bundle, and an unnamed but configured brand inherits it: the static
host serves that asset or the brand names its own `hero.src`. The summary
line and `--json` always say what was baked (`taxonomy: { source, file,
types, ids } | null`, `brand: { source, file, name } | null` — the paths,
never the contents; no operator path lands in the bundle). Proof:
`tools/test-studio-bundle.mjs` T8 compares a `--taxonomy` bundle with a
server started with the same file (body, header, the board byte-identical to
the `typed-canonical.mapped` golden of `tools/test-golden-board.mjs`), T8b a
`--brand` bundle's shell fragments with a branded server's, T4b the
unconfigured build with the same tree's build with the seams unset (byte for
byte), T9 the baked bundle in headless Chromium.

### Rebadge batch 4: baking the MCP settings policy and the MCP origin list

`--mcp-settings-policy <file.json>` bakes the MCP server-settings policy (§9,
the file a server reads from `OBSERVOGRAM_MCP_SETTINGS_POLICY`): read with one
leading byte-order mark stripped, parsed and compiled by
`compileSettingsPolicy` (`tools/lib/mcp-server-settings.mjs`) as
`server/mcp-settings-policy.mjs` does, plus the id clocks the server's
start-time load skips — a bad file fails the build with
`--mcp-settings-policy: <path>: <reason>`, the server's texts, and a pattern
a server loads can fail it as `rules[<i>].when: pattern too slow against a
256-character id` — and served by
the shim's `GET /api/mcp-settings` as `{ ok, proxy: false, policy, configured:
true }`. `--mcp-origins <origin>,…` bakes the origins the bundle's Server
settings modal may send settings to from a page not served on the MCP
server's machine (a bundle on a CDN configuring an https MCP server), read by
the server's list rule (`parseOriginList`, `tools/lib/mcp-url-safety.mjs`; `*`
any origin) — an entry that is not an http(s) origin fails the build, where a
server ignores it — and served beside the policy as `mcpOrigins: { listed:
true, origins }` (`origins` null for `*`). When a flag is absent
`OBSERVOGRAM_MCP_SETTINGS_POLICY` and `OBSERVOGRAM_MCP_ORIGINS` are honoured
(the legacy `TOMOGRAPH_` spelling too); a per-org list has no meaning in a
bundle. Both config keys are appended after `taxonomy` and only when baked,
so an unbaked build keeps its bytes (T4b). The summary line names the rule
count and the origins; `--json` adds `mcpSettingsPolicy: { source, file,
rules } | null` and `mcpOrigins: { source, origins } | null` — never the
policy's contents.

### Compare, the PromQL parser and the licences (follow-up compare-in-bundle)

**What the bundle answers.** Three computations a server makes are answered
in the browser by `studio/static-backend.mjs`, over the same `tools/lib`
engines, loaded at a route's first call (the boot does not evaluate them):
`GET /api/diff` (Compare: the diff and its traceability graph), `POST
/api/packs/:id/retrofeed` (the repository update from live — the one non-GET
the shim answers, computed and written nowhere) and `GET
/api/packs/:id/audit-report` (closing `B3.5-bundle-audit-report`, [`RELIABILITY_WORKFLOW.md`](RELIABILITY_WORKFLOW.md)). Pair
by name and by id needs no change: it re-keys the received diff in the
browser over the two packs, as on a server (closing `compare-modes-bundle`,
[`LIVE_FETCH.md`](LIVE_FETCH.md) §15.5). What is proven, and where it stops:

- The diff is the server's answer body for body — status, reason phrase,
  content type, the headers the server sets and the raw text — for the
  requests the studio sends. `tools/test-bundle-compare.mjs` and
  `tools/test-bundle-compare-pairs.mjs` compare it with a running server in
  Node, from the source (every ordered pair of ten packs in each scope mode
  the studio sends; every `scopeMode` spelling on four pairs; the
  environments; every refusal) and from a CLI-built file (its import map
  applied by a resolve hook, the shim imported from its own `data:` address),
  in every `npm test`, CI's included. Its C8 compares the in-page answer in
  headless Chromium under the browser locales `en-US`, `cs-CZ` and `et-EE`;
  it runs only where Playwright and its browser are installed, which CI's
  jobs are not. Nothing is proven in Firefox or Safari.
- Only with the baked taxonomy bound: a page where the studio could not
  compile the taxonomy built in answers the three routes 500 naming that,
  never an answer classified by the default families. The studio binds the
  taxonomy it is served without re-running the 50 ms timing check, which the
  builder (or a server) ran on the same document.
- Retrofeed's body is read as the server's parsers read it, case by case,
  but for three cases the studio never sends: a `Content-Encoding`, a JSON
  body in a UTF charset other than UTF-8, and a text body's charset.
- The audit report differs from a server's in declared fields only:
  `generator` (`<product> static bundle`), `pack.source` (`bundle`, or `url`
  for a `--pack-url` pack), `assessments` and `waivers` (`available: false`,
  "not recorded by this build": a bundle has no store — its `GET …/verdicts`
  still answers the empty document a server gives a never-registered pack,
  which is what a server would say of the pack, where the report says what
  this build can record), the clock's `generatedAt`, and for a pack a server
  has registered `tier.service`/`tier.environment` (`null`: a bundle has no
  registry).
- The diff runs on the page's main thread: the largest example pair
  (krystaline × production-curated) took 0.6–0.8 s in Chromium where it was
  measured.
- In the static posture Deploy explains instead of opening, every deploy
  control Compare, Diagnose and Remediate draw is drawn unavailable with the
  reason, and each remedy that would name a server action says how a bundle
  gets a live pack — addressed to the reader, who did not build the file
  (`studio/static-remedies.mjs`; `tools/test-static-remedies.mjs` holds every
  such phrase in the studio to a disposition).

**What the build needs.** The snapshot's whole tree, with `package.json`,
`package-lock.json`, `LICENSE` and `VENDOR-MANIFEST.json` from the same
upstream commit, and an `npm ci` at its root before the build. Coming from an
earlier snapshot:

1. Snapshot the whole tree as before; keep those four files from the same
   upstream commit as the rest.
2. Run `npm ci` at the tree's root (Node 22.16 or newer) before
   `node tools/build-studio-bundle.mjs`; on a build machine that needs no dev
   tools, `npm ci --omit=dev`. Either installs the server's production
   dependencies too (74 packages: express, openid-client, …), of which a
   bundle embeds four; an offline build machine needs all of them in npm's
   cache or a registry mirror (prime it once with `npm ci` online, then run
   `npm ci --offline`).
3. Build. The human summary line is unchanged; `--json` gains a last key,
   `thirdParty` — each embedded package's `name`, `version`, `license`,
   `entry` (its file inside the package) and `bytes`; no build-machine path.
4. If you patch an installed package (patch-package, a hand edit), the bundle
   embeds your patched file and the licence block does not mark it as
   modified; marking it where its licence asks is yours to do.
5. A pipeline that rewrites the HTML after the build (a minifier, a CDN
   optimiser) must keep the `#observogram-licenses` element; a step that only
   strips comments keeps it, since it is a script element.
   `verifyBundleNotices(html)`, exported by `tools/build-studio-bundle.mjs`,
   checks a finished file.
6. Fonts: a build now drops the shell's Google Fonts lines unless
   `--remote-fonts` (it kept them unless `--no-remote-fonts`). A build that
   wants them for online readers adds `--remote-fonts`; one that passed
   `--no-remote-fonts` needs no change.
7. Nothing else: no other flag, config key, Content-Security-Policy or host
   change (`data:` in `script-src` was already needed).

The build refuses a tree it cannot account for, with a sentence naming the
package and a fix that whoever runs the build can follow: no `package-lock.json`, one that
does not parse or is older than lockfile version 2; a package the lockfile
does not list or that is not installed; an installed version or licence id
that differs from the lockfile's; a package with no licence id or no licence
file; a second copy that a bundled package would load instead of the hoisted
one (the fix is an `overrides` entry in your `package.json`); an import a
package does not declare, a file inside a package, a `node:*` import; a
licence text that cannot be embedded (one holding `</script` or `<!--`); no
`LICENSE`; a missing or unparsable `VENDOR-MANIFEST.json`; no spec provenance
in `vendor/observability-pack-spec/VERSIONS.json`.

**What the build checks.** The packages a bundle embeds are the ones
`VENDOR-MANIFEST.json`'s `npm` field names for a bundled `tools/lib` module
(today `@prometheus-io/lezer-promql`, for `tools/lib/promql-lezer.mjs`) and
the packages those import (`@lezer/lr`, `@lezer/highlight`, `@lezer/common`);
nothing else under `node_modules` is read. Each is installed at the version
`package-lock.json` pins, declares the licence id the lockfile records, ships
a licence file, and is the copy its importers load. Each entry file is
embedded byte for byte as installed, as a `data:` module under the package's
own name — the build changes nothing in it — with the package's licence
files, any NOTICE file at its root and the copyright lines its file carries.
Observogram's MIT licence is embedded in every bundle, with or without
packages. Upstream's tests pin the licences it reviewed (each package's SPDX
id and the sha256 of its licence and NOTICE files: `THIRD_PARTY` in
`tools/test-bundle-compare.mjs`), so a licence change fails upstream's CI
until someone reviews it; your own build embeds whatever your lockfile
installs.

**What it does not check.** Whether those licences suit your distribution.
The packages' code. That the installed files are the ones the registry
publishes: the lockfile's `integrity` is the hash of a package's tarball, and
nothing npm leaves under `node_modules` records a file's, so a post-install
patch is embedded as installed, unmarked. NOTICE files outside the published
package: the build does not consult a package's source repository
(`@prometheus-io/lezer-promql` publishes no NOTICE file; the block prints each
package's source repository, so a reader can look there). The licences of the
packs, brand assets or fonts you build in. The vendored spec, whose schema
every bundle embeds, comes from a repository that publishes no licence file;
the block states its provenance and claims no licence for it.

**The licence block.** One `<script type="text/plain"
id="observogram-licenses">` element at the end of `<head>` — never executed or
rendered, read by `textContent` — and one comment right after the doctype that
points to it, for a person opening the file. Its text: a preamble naming the
build and the version, which says each package is embedded as `npm ci`
installed it from `package-lock.json` and is not compared with the package the
registry publishes; `==== Observogram <version> — MIT ====` and the `LICENSE`
text; for each package, in code-point order of its name, `==== <name>
<version> — <SPDX id> ====`, a `File:` line (the entry file and its import-map
key), a `Source:` line (the repository its `package.json` names, when that is
an `https:` URL), a `Copyright lines in the file:` line (when the file carries
any) and each licence file, then each NOTICE file, under `---- <file name>
----`; then `==== The ObservabilityPack spec ====` with the
upstream commit `vendor/observability-pack-spec/VERSIONS.json` records. No
path of the build machine enters the file, and two builds of one tree with one
`builtAt` are byte-identical. `verifyBundleNotices(html)` → `{ ok, packages,
problems }` checks that the file has one such element, in `<head>`; an
Observogram MIT section with the licence's grant and its disclaimer; one
section per package the import map carries — with its `File:` line and a
licence text — and none for a package it does not carry; and the pointer
comment's wording. It does not compare the texts with an installed tree.

**Size.** An empty bundle is 5,454,277 bytes (115 repository modules and the
four packages; `--remote-fonts` adds 372), up from 4,901,598 bytes (109
modules) before this follow-up, both without the font links (+11.3 %): the
parser and its packages, the traceability graph and the blast radius, the
audit report, retrofeed and the static posture's texts.
`tools/test-studio-bundle.mjs` holds a two-pack build under 6,000,000 bytes,
so a dependency that enters the graph unexpectedly is caught where it lands.

**On a server too: one collation.** Every `tools/lib` sort passes `'en'` to
`localeCompare` — the CLDR root order, which English does not tailor — so the
diff, the graph, canonical PromQL and the identity keys and behaviour hashes
built from it order text the same under every process and browser locale
(without it, a bundle read in a Czech browser ordered its diff differently
from the server that built its packs). A server whose process runs under a
locale that tailors Latin letters (Czech, Danish, Estonian, Lithuanian,
Hungarian, Slovak and the like) orders differently from before; `C`,
`C.UTF-8` and `en_*` do not move. On such a server, an artefact whose
identity key holds canonical PromQL, or a sorted list that now sorts
differently, gets a new key, so a verdict recorded on it before the upgrade
does not carry at the pack's next re-registration. Check the collation where
the server runs (`node -p "new Intl.Collator().resolvedOptions().locale"` in
its environment): `en`, `en-US` or `und` — nothing moves; otherwise, after
each pack's first re-registration on the new version, read its
`verdict.carry` audit row (`dropped`, `droppedCount`) and record those
verdicts again. `tools/test-vendor-manifest.mjs` refuses a `localeCompare(`
or `Intl.Collator(` under `tools/lib` that does not pass `'en'`.

**The image.** The Docker image carries `LICENSE` beside `package.json`; its
`node_modules` carries each installed package's own licence file.
