# Vendoring Observogram modules downstream

Some teams build their own studio around Observogram's scoring engines — a
different shell, a different stack (e.g. a TypeScript "ADO studio"), but the
same verdict semantics. Reimplementing the grade engine is the fastest way to
drift from it, so the supported path is to **vendor the engine files verbatim**
(e.g. into a `packages/upstream/` directory downstream) and re-copy them when
this repo moves.

This document is the contract that makes that safe: which files are
vendorable, what each one needs from the host, and which seams this repo
promises to keep stable.

A downstream that keeps the whole repository and runs it as its product
follows [`DOWNSTREAM_REFRESH.md`](DOWNSTREAM_REFRESH.md) to refresh it.

## The manifest

Since 2026-10 the `tools/lib` part of this contract is machine-readable:
[`VENDOR-MANIFEST.json`](../VENDOR-MANIFEST.json) lists every pure module
under `tools/lib` a downstream may copy — sha256, byte size, exported names,
intra-set imports, npm dependencies — with the package version it belongs to
and the modules that are excluded, each with its reason. It is generated by
`npm run vendor-manifest`, guarded by `tools/test-vendor-manifest.mjs` in
`npm test`, and [`DOWNSTREAM.md`](DOWNSTREAM.md) is the workflow built on it
(snapshot → verify hashes → smoke → bump). The `tools/lib` rows of the table
below are a subset of the manifest; the table keeps the studio rows and the
prose contracts that follow.

**Additive keys on `compareBranches` output.** `tools/lib/traceability-graph.mjs`
itself is not in the vendorable set (it imports the PromQL parser), but its
result is the `diff.traceabilityGraph` a vendored `computeDiagnosticGrade`
scores Drift-free on and the input `branchRecordsFromGraph` reads, so its
shape is part of this contract. Since 2026-09 it keeps its original shape
and gains optional keys a downstream host may ignore: on every node verdict
`blastRadius` (the blast-radius `summary` — `{ slos, alerts, panels,
dashboards, routes, remediations, total }` — or `null`) and `ladder`
(`{ rung, status, detail }`), appended after `deltas`; on every branch
`ladderVerdict`, `ladderIntegrity` and `ladderIntegrityPct` beside
`verdict` / `integrity` / `integrityPct`; on the rollup `ladder = { healthy,
degraded, broken, unobserved, integrityMean, integrityPct }`, appended last.
`integrity`, `verdict`, `counts`, node `status` and `rollup.integrityMean`
are byte-identical with and without the annotations the ladder reads
(pinned in `tools/test-traceability-graph.mjs`), and Drift-free still reads
`rollup.integrityMean` — the switch to `rollup.ladder.integrityMean` is a
proposal (`docs/SCORING_PROPOSAL_LADDER_INTEGRITY.md`, gradeSchema 6), not
applied. Keys are only ever added here, never renamed or removed.

**Additive keys on `partialLiveEvidence(packB)`.** The result keeps its
original shape (`isLiveDraft`, `failed`, `empty`, `attempted`, `partial` —
`partial` still means *outright probe failures only*) and gains optional keys
a downstream host may ignore: `unsupported` (probe families the MCP tier does
not expose, from `mcp.probesUnsupported`), `errors` (`{ family: message }`
from `mcp.probeErrors.<family>`), and `vantage` — `'full'` (nothing failed,
nothing unsupported), `'partial'` (some probes failed), `'restricted'` (nothing
failed, some families not exposed), `'lost'` (every attempted family failed or
is unsupported), `'none'` (not a live draft). Keys are only ever added here,
never renamed or removed.

**Optional inputs `computeDiagnosticGrade` reads.** The diff-bucket path
counts a layer bucket's optional `scaffold` array (placeholders `diffPacks`
parks before pairing) into its `N scaffold excluded` note; older diffs without
it still pass through the `isScaffoldDiffEntry` filters. It counts the
optional `notObserved` array the same way (`N not checked`): artefacts one
pack holds in a family the other could not observe move no weight. The Fresh criterion
appends the live vantage to its `detail` (`vantage lost …` / `vantage partial
…`) read through `partialLiveEvidence` from the same module — the pass/fail
and every score are unchanged, and no import was added.

**Grade schema 5 (0.8.33): Multi-modal and Comprehensive earn by how far
they get.** `computeDiagnosticGrade` returns `gradeSchema: 5` (the new export
`GRADE_SCHEMA`). Both criteria gain `score` (0..1, read by `criterionScore`):
Multi-modal the signal kinds declared of four, Comprehensive the exact average
observed across the posture's four layers (the detail still prints it rounded).
`pass` keeps its bar (three kinds, 50 in 100). Against schema 4 a pack below a
bar gains (krystaline's 48% coverage: 0 → 0.48 of a point) and one above it
short of four kinds or of every mechanism loses (3 kinds: 1 → 0.75). The board
(`studio/overview-model.mjs`) no longer letters by a run scored under another
schema: `runGradesBoard` is false for it, the board grades the repository
alone and says *how the grade scores changed since the last live check*, and a
service-list row says *graded before the grade changed how it scores* (the
journeys listing's `lastRun.gradeSchema`, new). A record that names no schema
is not judged by it.

**Grade schema 4 (0.8.7): Chaos-validated tells declared from proven.**
`computeDiagnosticGrade` returns `gradeSchema: 4`. A declared experiment earns
`CHAOS_DECLARED_CREDIT` (0.25); the rest of the point needs a passing run inside
`CHAOS_PROOF_WINDOW_DAYS` of its schedule, from the experiment's spec 1.5
`last_result` or from `mcp.chaos.runs` on Pack B (the live run feed; it wins);
a failed newest run earns 0. The new exports are pure and import nothing:
`chaosProof(experiments, { nowMs, liveRuns })`, `liveChaosRuns(annotation)`,
`CHAOS_PROOF_WINDOW_DAYS` and `CHAOS_DECLARED_CREDIT`. Chaos-validated gains
`score` and `proof` (`{ state, score, pass, declared, fresh, provenAt, source,
failed, stale, never }`). A host with no run anywhere sees a declared pack lose
0.75 of a point against schema 3.

**Grade schema 3 (0.8.5): scaffolds earn nothing.** `computeDiagnosticGrade`
returns `gradeSchema: 3`; scores can fall, never rise, against schema 2 on the
same packs. Calibrated and Chaos-validated skip artefacts whose `source` is

id or title; the SLOs the scan invents from an alert name (`crawler.scaffold.slos.*`,
an objective of defaults) earn Calibrated nothing either. Two criteria gain optional
keys a host may ignore: Calibrated's
`baselines` (`{ declared, scaffolds }`, and `studio: { profile, mttd, mttr }` whenever

whole minutes from 1m to a week, else they count nothing — and the repository
states no baselines of its own; they counted only where the criterion is graded,
`applies !== false`, as `tools/lib/journey.mjs` and `overview-model.mjs`

## The design system

The studio's look is three files a downstream app copies verbatim, so its
screens read as the same product without a theme of its own to maintain:

1. **`design-tokens.css`** — every value, and only values: the palette, the
   type and the measures as `--og-*` custom properties on `:root`, restated
   for `[data-theme="dark"]`. No rule styles an element. Names are semantic
   (`--og-accent`, `--og-second`, `--og-warn`, `--og-fail`, `--og-info`,
   each with `-bg`; `--og-bg`, `--og-panel`, `--og-line`, `--og-text`,
   `--og-muted`; `--og-font`, `--og-font-code`; `--og-radius-*`,
   `--og-control-*`, `--og-button-*`, `--og-stat-*`), so a host changes a hue
   by overriding a token, never by editing a rule. `design-tokens.json`
   carries the same values (`themes.light` / `themes.dark`, names without
   the prefix); regenerate it with `node tools/gen-design-tokens.mjs --write`.
2. **`design-kit.css`** — the pieces, as `.og-*` classes that read the tokens
   and nothing else: no global rule, no element selector, no positioning, so
   it cannot collide with a host's own stylesheet. Put `.og-app` on the root.
3. **`design-bridge.css`** — for the view stylesheets you already vendor:
   `verdict-ui.css` and `proto.css` expect a set of theme properties from the
   host; this file defines all of them from the tokens. Load it *after* them.

```html
<link rel="stylesheet" href="design-tokens.css">
<link rel="stylesheet" href="verdict-ui.css">   <!-- and any other vendored view styles -->
<link rel="stylesheet" href="design-kit.css">
<link rel="stylesheet" href="design-bridge.css">
```

Set `data-theme="dark"` (or `"light"`) on `<html>`. `studio/reskin.css` is
**not** vendorable: it is this studio's adapter, mapping its own chrome names
and legacy classes onto the tokens. A downstream host writes its own adapter
only for markup it already has; new markup uses the `.og-*` classes.

`tools/test-design-system.mjs` holds each file to its role in CI: the tokens
file contains nothing but tokens, both themes define every colour, the JSON
equals the CSS, the kit and the bridge read tokens only, the adapter decides
no colour of its own, and no stylesheet reads a token that does not exist.

## The Overview board

The studio's front door — one service, the machine drawn as three columns
under *Discover · Diagnose · Remediate* — is vendorable as a unit: the model,
the renderer, the loaders, the state-free kit pieces it emits and its
stylesheet, on top of the design system above. `tools/test-overview-model.mjs`
holds the set in CI: the import closure of each file is exactly the one the
table lists, the model and the pure kit touch no DOM, and `overview.css`
reads design tokens and its own `--ov-*` properties only.

**The model takes its inputs explicitly** and returns words and numbers, never
markup:

```js
buildOverviewModel({
  services, servicesStatus, catalog,            // GET /api/services rows and their status; the pack catalogue
  serviceId, env, isLiveAggregatePack,          // the row and environment on screen; your rule for aggregate packs
  diagnostic, diagnosticError, decision,        // computeOverviewDiagnostic(layered) and its causes (or the read error)
  journeys, journeysError, run,                 // GET /api/journeys and the service's newest run record
  running, startError, pending,                 // a check in flight, a refused start, facts still being read
  layout, cells, layered, conformance, conformanceError,   // 'board' | 'simple'; computePostureMatrix(layered).cells; the layered pack; GET /api/packs/:id/conformance
  unkinded,                                     // computePostureMatrix(layered).unkinded (optional: below)
  access, start, startable,                     // the reader's rank ({ canWrite, reason }); the start's state; true when you run the start (below)
  listable,                                     // true when you draw the service list as the front door (below): the header links back
  gradeSwitches,                                // true when you wire setGradeCriterion (below): the board offers a switch on each criterion
  now, productName,
});
```

`unkinded` is the matrix's list of the artefacts with no kind of signal of
their own (an alert route, a pipeline receiver, the OTel SDK, baselines;
`MECHANISM_BY_ID_PREFIX` in `studio/diagnostic-grade.mjs` says which). With
it, *Unplaced* counts them beside what could not be placed on a layer, and
the Discover column adds up: the plates plus *Unplaced* are *Declared*,
each artefact once. Without it, *Unplaced* counts only the artefacts with
no layer, as before 2026-11-04.

The shapes are the ones the fixtures under `tools/fixtures/overview/` carry
(`services.json`, `packs.json`, `journeys.json`, a real run, a half-blind
run, the posture cells as counts, a conformance body). Percentages stay
numbers in the model (`alignmentPct`, `coveragePct`); the renderer puts the
sign on them. The vocabulary rule the test walks — no layer code, artefact
id or engine state word in any string — is part of the contract.

**The renderer** is `renderOverview(container, model, host)`: `container` is
any element (the test uses a 20-line shim with `innerHTML` and one click
listener), and the actions ride on `host.overview`, an object a host fills
with its own implementations:

```js
host.overview = {
  selectService(id), selectEnv(name),           // the picker and the environment switch
  checkNow(),                                   // Check again → runServiceCheck, then re-read the facts
  openDiscover(compare), openDiagnose(compare), openRemediate(compare),   // the column links (compare: below)
  openRules(compare),                           // Remediate's "See the rules in Expert": the specification's rules (Conformance)
  openNeuron(),                                 // "See the differences"
  expert(), retry(),                            // the mode switch; the Retry of an unreadable listing
  scan(), live(), upload(slot), resetStart(),   // the start's ways in (below): your repo scan, your live draft, your upload into 'a' or 'b'; Change Pack A
  explain(reason),                              // a start card the reader's rank cannot use, activated
  backToList(),                                 // ← Services, with `listable` (the service list: below)
  setGradeCriterion(key, { graded, reason }),   // with `gradeSwitches`: a criterion off (graded: false, a reason) or on again for the service on the board
  toggleControlRoom(),                          // with `controlRoom`: the board's Control room button
  closeControlRoom(), refreshControlRoom(),     // the panel's Close (and Escape) and Refresh (control-room-view.mjs)
  setTargets(),                                 // with `listable`, to a rank that may write: the MTTD / MTTR tile's Set targets… /
                                                // Change targets… and the control room's (`controlRoomMttx({ settable })`): open the
                                                // targets-only form: targetsFormOpened(services, { serviceId, env }), saved by
                                                // targetsOnlyPlan(values, { services, serviceId }) → PATCH { targets } alone;
                                                // called with 'board' or 'control-room' (where the focus goes back)
};
```

**The control room** is opt-in: `buildOverviewModel({ controlRoom: true,
controlRoomOpen })` adds `model.controlRoom = { offered, open, reason }` and
the board draws its button (unavailable, with the reason, when the picked
environment names no live endpoint or `access.canWrite` is false; the same
rule is `controlRoomOffer(picked, access, open)`, for closing an open panel
when the board moves to an environment it is not offered for). The panel
is yours to place: give it its own element (not the board's container, which
repaints), drive it with `createControlRoomDriver` (control-room-api.mjs), and
draw `buildControlRoomModel(...)` with `renderControlRoom`. Its `mttx` is
`{ declared, mttdTarget, mttrTarget, runs: [{ experiment, at, outcome,
environment, mttd }] }` (the targets the repository states, as spec
durations, and every chaos run recorded there; the studio takes them from
`declaredByTier(layered).mttx`, whose new `runs` key lists them newest
first), or `{ unread: true }` while the service's pack is not read; the
model picks the run of the panel's environment. Place it with
`placeControlRoom(head)` (control-room-view.mjs) after the board is drawn,
`head` the board's `.ov-head`: it sets `--ov-cr-head` on the document so the
panel starts below the context bar and its door stays in sight (the panel's
top is `12px + --ov-cr-head`; the studio's chrome adds its own bars in
`ux.css`). While it is open, put `ov-cr-open` on an ancestor of the board
(the studio puts it on `<body>`): from 2040 px the board then makes room
for the panel. Its data is the
server's `POST /api/services/:id/control-room`; a server of your own adds
families with `OBSERVOGRAM_CONTROL_ROOM_FAMILIES` (README, *The control
room*), and the panel draws any family the answer carries, by its id and title.

**Criteria a service is not graded on.** A service record may carry
`gradeOff: [{ key, reason, by, at }]` (README, *Criteria a service is not
graded on*), and the engine takes the same as `opts.off`:
`computeDiagnosticGrade(packA, packB, posture, catalogBId, diff, { off })` —
keys, or objects with a `key` (`gradeOffKeys` normalises; `GRADE_CRITERIA`
and `GRADE_CRITERION_KEYS` are the vocabulary). A criterion left out is
still computed and listed, marked `applies: false` and `informational: true`
(a renderer that already draws Operability's row as shown-not-scored draws it
the same way), and leaves the sums and the totals; `overall.off` names what
was left out. Without `off` the output is byte for byte what it was. The
board needs nothing from you to honour the switches: `buildOverviewModel`
reads them from the picked service's row and hands them to `gradeModel`,
`gradeWhy` and `boardComparison` (`off`). Two things are yours: compute the
pack-alone grade with them — `computeOverviewDiagnostic(layered, posture,
{ off: service.gradeOff })` — and, to let the reader switch, pass
`gradeSwitches: true` and implement `setGradeCriterion`: send the service's
whole list (`PATCH /api/services/:id { gradeOff: [{ key, reason }] }`), read
the services again, repaint, and run a check, because a run record that
graded on other criteria (`grade.off`) is not the board's letter
(`runGradesBoard(run, pack, off)`). Build the list from the record as the
server has it then (`loadService(id)`), not your copy, and send one switch at a
time. Where `gradeWhy` offers no lines, the model's `grade.graded` lists the
criteria graded by name and the board draws each with its switch. Without
`gradeSwitches` the board lists what is off and offers no switch. Expert's verdict takes the same keys:
`buildVerdictModel({ …, gradeOff })` and `projectGrade(uids, { …, gradeOff })`.
The studio's wiring is `setOverviewGradeCriterion` and `gradeServiceInFocus` in
`studio/app.mjs`.

Expert's Diagnose (`compare-view.mjs`, with the pure `assessment-page.mjs`
and `grade-criteria-ui.mjs`) grades with `state.gradeOff` (the keys) and says
what is off from `state.gradeService` — the record whose primary pack is on
screen (`{ id, name, gradeOff: [{ key, reason, by, at }], setAside: [...] }`), or
`null`. Against a live Pack B it grades the comparison without the record's
set-asides (`set-asides.mjs` `applySetAsides`), lists the differences with a
switch each (the same what-if), and Remediate's plan leaves them out. Each
scored row of its checks carries a switch, and a switch is a what-if: the
grade on screen is taken again over the set tried, in the page, and nothing is
sent. **Keep** is offered only when the host fills the optional
`host.setGradeCriteria(serviceId, { off, reason, setAside })` — `off` the
keys the service is not graded on from now on, `reason` for those newly left
out, and, when the what-if changed them, `setAside`, the whole list of
set-asides (`PATCH /api/services/:id { setAside }`): build the criteria's
list from the record as the server has it (a criterion that stays off keeps
its reason, so its who and when), save both in one request, read the services
again, repaint, and resolve `true` (`false` when nothing was saved).
Without the hook, or in a static bundle, the switches still try a what-if and
the page says it is not saved. (0.8.23's `host.setGradeCriterion`, one
criterion at a time, is replaced by it.)

A hook a host does not supply is a no-op (the view calls them optionally).

The board reads a service record's `setAside` too (`buildOverviewModel`, by
`serviceAsideKey`): a run whose `grade.setAside.fingerprint` names other
set-asides than the record's now is not its letter, and its counts and its
sentence say how many the run set aside (`drift.setAside`). A host whose
records carry no `setAside` reads none, as before.

The three column links hand their hook `model.compare`: the comparison the
board graded, so the view the host opens can show the same one. It is
`{ packBId, envB, label }` — the live pack the journey's last run read, with
`envB` `null` because the run adapted Pack B with no environment — or
`null`. `boardComparison({ journey, run, catalog, pack })` decides it, and it
is set only when all of these hold:
- the journeys listing names a `livePack: { id, label, refreshedAt }` for the
  journey (Observogram's server keeps every live run's Pack B as one);
- `refreshedAt` is the read the board's run names (`packB.refreshedAt`);
- that run is the board's letter (`runGradesBoard`: it graded this pack and
  its live side did not shrink since the check before);
- the catalogue has the pack.

A host whose listing has no `livePack` always gets `null`, and a hook that
ignores the argument opens what it opened before. Only a column link
carries the id; the vocabulary rule skips `compare`, and nothing renders it.
At most one `.og-btn--primary` is drawn in any state, and as many as the
model's `primary` says; the simple layout is drawn instead of the board when
`model.layout` is `'simple'`, when the service's only pack is a live
aggregate's, or when the board throws (the error is logged and the screen
never goes blank).

**The start** is the drift check run from the board when there is nothing to
grade — no service, or a service with no pack at all: step 1 lands Pack A (a
repo scan or an upload), step 2 Pack B (a live draft or an upload), step 3
is your comparison of the two. It is opt-in: without `startable: true` the
board draws what it always did — *No service to show yet* and *Open Expert
mode* — so a host that copies a newer board before wiring the start loses
nothing. With it, the model carries `start` and the view draws the three
steps in place of the panels; a card whose hook you do not supply is drawn
unavailable (*Not offered here*), never one that does nothing. The flows are
yours; the routing is the model's, so every host keeps Pack A and pairs the
packs alike:

```js
import { START_IDLE, startChoose, startAdopted } from './overview-model.mjs';

let start = START_IDLE;                         // keep it beside the model's other inputs
host.overview.scan = () => { start = startChoose(start, 'a'); openYourScan(); };
host.overview.live = () => { start = startChoose(start, 'b'); openYourLiveDraft(); };
host.overview.upload = (slot) => { start = startChoose(start, slot); openYourFilePicker(); };
host.overview.resetStart = () => { start = START_IDLE; repaint(); };

// When one of those flows registers a pack while the board is on screen:
const { start: next, compare, said, refused } = startAdopted(start, { id, label });
start = next;
if (compare) runYourCheck(compare.a.id, compare.b.id);         // step 3 (the studio: below)
else repaint();                                                 // Pack A in: step 2 opens
announce(said);                                                 // `refused`: the same pack offered as Pack B

render(buildOverviewModel({ ...facts, access, start, startable: true }));
```

Registering Pack A usually creates its service; the model keeps the start
on screen while `start.a` is set, so the board does not jump to an empty
service between the steps. Step 3 is the host's; the studio keeps it on the
board: it saves the pair as the service's check (`POST /api/journeys/capture`,
named `<service>-repo-vs-live`), re-reads the board's facts and runs the check
(`runServiceCheck`), so the board shows the grade against live and what to
change; `journeyForService` prefers a check of the service's own pack, so the
saved one is the one shown. The studio's wiring is `overviewActions`,
`overviewStartAdopt` and `overviewStartCheck` in `studio/app.mjs`: its scan,
its live job (a finished job's pack is Pack B), its file upload (a file
dropped on the page while the start is up fills the next step). The static bundle (DOWNSTREAM.md
§10) does not draw Overview: its shim answers the services and journeys
routes with 501.

**The service list** is Overview's front door where the services table
exists: one row per service and environment with its two places — the
repository (`repository` on the service record: GitHub, Azure DevOps or a
folder on the server) and the live MCP endpoint (the environment's
`mcpEndpoint`) — its last check, and *Run*, *Open*, *Change*; *Add a service*
is the form of five answers (the fifth, the MTTD / MTTR targets, saved on
the service record as `targets`; the board's tile takes them as
`chainModel({ layered, targets, env, settable, counted })`, after the repository's own, with the
environment's newest chaos run beside them, and `buildOverviewModel` sets
`counted` (`studioTargetsCounted(diagnostic) === true`: the tile then says the
grade counts them) and `settable` from `listable` and the reader's rank, so the tile offers *Set
targets…* / *Change targets…* to `host.overview.setTargets()`; pass `targetsTouched` from the
form to `savePlan` so an *Add* that completes a record never replaces the
targets it has with the form's own start). It is opt-in like the start: without
`listable: true` the board's header has no way back, and nothing else
changes. The models are pure; the state (the form, which row runs, whether
the board or the list is on screen) is the host's:

## Contracts this repo keeps stable

- **The state-slice signatures above.** New inputs arrive as new optional
  keys, never as global reads.
- **The `initHost` hook names** (`loadPackB`, `openDeployModal`,
  `renderMainView`, `renderTabs`) — the host object never becomes a mirror
  of app.mjs (docs/UI_CONVENTIONS.md).
- **Design token and kit names.** `--og-*` properties and `.og-*` classes
  are only ever added, never renamed or removed; token names stay semantic
  (a role, not a colour word — CI rejects `--og-lime`). `design-tokens.json`
  keeps `version: 1` while that holds. Values (a hue, a radius) may change:
  that is a re-copy, not a migration.
- **Pack annotation namespace** — writers emit `observogram.*`
  (`observogram.diff.scopeMode`, `observogram.retrofeed.*`,
  `observogram.services`, `observogram.unobserved.<kind>`); readers keep
  accepting the pre-rebrand `tomograph.*` keys.
- **Diff buckets and entry fields are only ever added.** `notObserved`
  (per layer, and `summary.notObserved`) is the latest: a host whose live
  pack comes from its own fetcher gets it by writing
  `observogram.unobserved.<kind>` = reason for every artefact family that
  fetcher cannot look at (docs/DIFF.md); a host that writes none sees an
  empty array and the counts it always had. A metric family's entry adds
  `series` and `memberIds` to the artefact it embeds; a consumer that lists
  a pack's own artefacts beside the diff uses `memberIds` to give every
  series its family's status (the studio's Compare does). `declaredAhead`
  (per layer, and `summary.declaredAhead`) came after it, and those keys exist
  only when a pack carries a lifecycle statement (docs/DIFF.md).
- **`L4_SUBGROUPS`** is intentionally duplicated: `constants.mjs` owns the
  display copy, `diagnostic-grade.mjs` inlines a private copy so it stays
  zero-import. Change both or neither.
- **Env/header compat** for downstream servers proxying Observogram: every
  `OBSERVOGRAM_*` env var also honors its `TOMOGRAPH_*` spelling
  (`tools/lib/brand-env.mjs`), and the server accepts both
  `X-Observogram-Org`/`X-Observogram-CSRF` and the legacy `X-Tomograph-*`
  headers (echoing `X-Observogram-Org`).

### Sequential calls

The hook's `fetchImpl` sees every MCP request, and `OBSERVOGRAM_TRANSPORT_HOOK` loads
one module, so add the queue to the module that already prepares your gateway requests.
Two things differ from your patch. The timeout (`MCP_TIMEOUT_MS`, 30 seconds by default,
at most 300 seconds) starts when a request enters the queue, not when it reaches the
wire, so raise it to cover the wait. The transport is one per process, so the queue
serialises across every live job the server runs (up to four), not per fetch.

### Scope variables

```bash
OBSERVOGRAM_SNAPSHOT_METRIC_EXCLUDE='^demo_event_(?:\d+|blank)_total$'
OBSERVOGRAM_SNAPSHOT_FOLDER_UIDS=folder-a
OBSERVOGRAM_SNAPSHOT_RULE_GROUPS='Group One,Group Two'
```

- `METRIC_EXCLUDE` takes white-space-separated patterns, each anchored and bounded. It
  runs after `METRIC_PREFIXES`.
- `RULE_GROUPS` is a comma list, compared exactly, so a name may hold spaces.
- These values describe one team, service and environment. Keep them in the deployment's
  variables or in `OBSERVOGRAM_ORG_<KEY>_SNAPSHOT_*`, not in code ([`LIVE_FETCH.md`](LIVE_FETCH.md) §15.2).
- The two variables your patch read inside `fetchMcp` do not exist upstream.
- After the first snapshot, read the gate log. It says whether the folder scope was pushed
  down or the rules were read whole.
- **Not built:** no tool in the capability registry takes a rule group or a folder title,
  so the rule-group and recording-rule tools your patch called were not added. Read
  `observogram.live.gaps`. If recording rules are missing, send the tool's recorded answer
  (`npm run record-fixtures -- --write`) so it can get a registry row. A hunk that calls an
  unregistered tool fails `tools/test-contract-guard.mjs`.

### Exporter manifests

`metrics-manifest.json` ([`EXPORTER_METRICS.md`](EXPORTER_METRICS.md) §18.1): `static_metrics` becomes `metrics`, or comes from
`packc emit --exporter`, and `dynamic_families` becomes `dynamicFamilies`.

- A pattern must be anchored and open with a literal prefix of at least three characters
  that a platform does not own (`^node_` is refused, `^node_hwmon_` is not). An entry
  that breaks a rule is a crawl warning and is not read.
- Names are tested as listed. Your patch lowercased the live name first, so check any
  pattern that relied on that.
- Members count in `jaccard` and `alignment`, and `summary.dynamicFamilies.members` says
  how many pairs rest on a pattern.
- Key on `spec.origin_kind: exporter-family`, not on the `METRIC-FAM-` id prefix.

### Lifecycle blocks

- **Move the block to the top of the file.** Only comments, `---` and Helm directives may
  sit above it. Lower down it is a warning and parks nothing.
- **Use only `deployed`, `planned` or `not-deployed` as states.** Any other word is a
  warning and parks nothing. `maturity` is optional.
- **Expect some rules to stay visible.** A symbol parks only when every file that speaks
  for it carries the same deployment, readers included. If an alert or a dashboard in a
  file with no block reads a rule, that rule still reads *declared, not live*.
- **A `PrometheusRule` custom resource is not walked.** A block in one does nothing, and a
  rule in one does not keep a series visible.
- **Update what reads the diff.** The pack carries one `observogram.lifecycle` annotation,
  not `.sources` and `.symbols`. `summary.lifecycleEnvironment` is now
  `summary.lifecycleEnvironments`, an array. Every new key exists only when a pack carries
  a statement, so read them as optional.
- **Name the environment.** `diffPacks` now takes `opts.environment`. Without it the
  statement must hold for both packs' environments, and a live pack is always bound to
  `prod`, so a staging comparison should pass `environment`.

### What will read differently

Compare a pack before and after the bump, and expect these to move:

- An exporter's name no longer widens a service's scope, and a live dashboard now reaches
  the scope through its panel expressions (#185, #186).
- Parked artefacts leave the union, so `alignment` rises by what is parked. A statement
  does not expire. Set `gate.maxDeclaredAhead` on any journey whose gate you rely on.
- A repository metric your exclude patterns match, or a rule of another group, reads as
  *not checked* rather than as drift.
