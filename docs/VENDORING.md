# Vendoring Observogram modules downstream

Some teams build their own studio around Observogram's scoring engines — a
different shell, a different stack (e.g. a TypeScript "ADO studio"), but the
same verdict semantics. Reimplementing the grade engine is the fastest way to
drift from it, so the supported path is to **vendor the engine files verbatim**
(e.g. into a `packages/upstream/` directory downstream) and re-copy them when
this repo moves.

This document is the contract that makes that safe: which files are
vendorable, what each one needs from the host, and which seams this repo
promises to keep stable.

## The manifest

Since 2026-10 the `tools/lib` part of this contract is machine-readable:
[`VENDOR-MANIFEST.json`](../VENDOR-MANIFEST.json) lists every pure module
under `tools/lib` a downstream may copy — sha256, byte size, exported names,
intra-set imports, npm dependencies — with the package version it belongs to
and the modules that are excluded, each with its reason. It is generated by
`npm run vendor-manifest`, guarded by `tools/test-vendor-manifest.mjs` in
`npm test`, and [`DOWNSTREAM.md`](DOWNSTREAM.md) is the workflow built on it
(snapshot → verify hashes → smoke → bump). The `tools/lib` rows of the table
below are a subset of the manifest; the table keeps the studio rows and the
prose contracts that follow.

## The design system

The studio's look is three files a downstream app copies verbatim, so its
screens read as the same product without a theme of its own to maintain:

1. **`design-tokens.css`** — every value, and only values: the palette, the
   type and the measures as `--og-*` custom properties on `:root`, restated
   for `[data-theme="dark"]`. No rule styles an element. Names are semantic
   (`--og-accent`, `--og-second`, `--og-warn`, `--og-fail`, `--og-info`,
   each with `-bg`; `--og-bg`, `--og-panel`, `--og-line`, `--og-text`,
   `--og-muted`; `--og-font`, `--og-font-code`; `--og-radius-*`,
   `--og-control-*`, `--og-button-*`, `--og-stat-*`), so a host changes a hue
   by overriding a token, never by editing a rule. `design-tokens.json`
   carries the same values (`themes.light` / `themes.dark`, names without
   the prefix); regenerate it with `node tools/gen-design-tokens.mjs --write`.
2. **`design-kit.css`** — the pieces, as `.og-*` classes that read the tokens
   and nothing else: no global rule, no element selector, no positioning, so
   it cannot collide with a host's own stylesheet. Put `.og-app` on the root.
3. **`design-bridge.css`** — for the view stylesheets you already vendor:
   `verdict-ui.css` and `proto.css` expect a set of theme properties from the
   host; this file defines all of them from the tokens. Load it *after* them.

```html
<link rel="stylesheet" href="design-tokens.css">
<link rel="stylesheet" href="verdict-ui.css">   <!-- and any other vendored view styles -->
<link rel="stylesheet" href="design-kit.css">
<link rel="stylesheet" href="design-bridge.css">
```

Set `data-theme="dark"` (or `"light"`) on `<html>`. `studio/reskin.css` is
**not** vendorable: it is this studio's adapter, mapping its own chrome names
and legacy classes onto the tokens. A downstream host writes its own adapter
only for markup it already has; new markup uses the `.og-*` classes.

`tools/test-design-system.mjs` holds each file to its role in CI: the tokens
file contains nothing but tokens, both themes define every colour, the JSON
equals the CSS, the kit and the bridge read tokens only, the adapter decides
no colour of its own, and no stylesheet reads a token that does not exist.

## The Overview board

The studio's front door — one service, the machine drawn as three columns
under *Discover · Diagnose · Remediate* — is vendorable as a unit: the model,
the renderer, the loaders, the state-free kit pieces it emits and its
stylesheet, on top of the design system above. `tools/test-overview-model.mjs`
holds the set in CI: the import closure of each file is exactly the one the
table lists, the model and the pure kit touch no DOM, and `overview.css`
reads design tokens and its own `--ov-*` properties only.

**The model takes its inputs explicitly** and returns words and numbers, never
markup:

```js
buildOverviewModel({
  services, servicesStatus, catalog,            // GET /api/services rows and their status; the pack catalogue
  serviceId, env, isLiveAggregatePack,          // the row and environment on screen; your rule for aggregate packs
  diagnostic, diagnosticError, decision,        // computeOverviewDiagnostic(layered) and its causes (or the read error)
  journeys, journeysError, run,                 // GET /api/journeys and the service's newest run record
  running, startError, pending,                 // a check in flight, a refused start, facts still being read
  layout, cells, layered, conformance, conformanceError,   // 'board' | 'simple'; computePostureMatrix(layered).cells; the layered pack; GET /api/packs/:id/conformance
  unkinded,                                     // computePostureMatrix(layered).unkinded (optional: below)
  access, start, startable,                     // the reader's rank ({ canWrite, reason }); the start's state; true when you run the start (below)
  listable,                                     // true when you draw the service list as the front door (below): the header links back
  now, productName,
});
```

`unkinded` is the matrix's list of the artefacts with no kind of signal of
their own (an alert route, a pipeline receiver, the OTel SDK, baselines;
`MECHANISM_BY_ID_PREFIX` in `studio/diagnostic-grade.mjs` says which). With
it, *Unplaced* counts them beside what could not be placed on a layer, and
the Discover column adds up: the plates plus *Unplaced* are *Declared*,
each artefact once. Without it, *Unplaced* counts only the artefacts with
no layer, as before 2026-11-04.

**The renderer** is `renderOverview(container, model, host)`: `container` is
any element (the test uses a 20-line shim with `innerHTML` and one click

A hook a host does not supply is a no-op (the view calls them optionally).

The three column links hand their hook `model.compare`: the comparison the
board graded, so the view the host opens can show the same one. It is
`{ packBId, envB, label }` — the live pack the journey's last run read, with
`envB` `null` because the run adapted Pack B with no environment — or
`null`. `boardComparison({ journey, run, catalog, pack })` decides it, and it
is set only when all of these hold:
- the journeys listing names a `livePack: { id, label, refreshedAt }` for the
  journey (Observogram's server keeps every live run's Pack B as one);
- `refreshedAt` is the read the board's run names (`packB.refreshedAt`);
- that run is the board's letter (`runGradesBoard`: it graded this pack and
  its live side did not shrink since the check before);
- the catalogue has the pack.

A host whose listing has no `livePack` always gets `null`, and a hook that
ignores the argument opens what it opened before. Only a column link
carries the id; the vocabulary rule skips `compare`, and nothing renders it.
At most one `.og-btn--primary` is drawn in any state, and as many as the
model's `primary` says; the simple layout is drawn instead of the board when
`model.layout` is `'simple'`, when the service's only pack is a live
aggregate's, or when the board throws (the error is logged and the screen
never goes blank).

**The start** is the drift check run from the board when there is nothing to
grade — no service, or a service with no pack at all: step 1 lands Pack A (a
repo scan or an upload), step 2 Pack B (a live draft or an upload), step 3
is your comparison of the two. It is opt-in: without `startable: true` the
board draws what it always did — *No service to show yet* and *Open Expert
mode* — so a host that copies a newer board before wiring the start loses
nothing. With it, the model carries `start` and the view draws the three
steps in place of the panels; a card whose hook you do not supply is drawn
unavailable (*Not offered here*), never one that does nothing. The flows are
yours; the routing is the model's, so every host keeps Pack A and pairs the
packs alike:

import { START_IDLE, startChoose, startAdopted } from './overview-model.mjs';

host.overview.upload = (slot) => { start = startChoose(start, slot); openYourFilePicker(); };

Registering Pack A usually creates its service; the model keeps the start
on screen while `start.a` is set, so the board does not jump to an empty
service between the steps. Step 3 is the host's; the studio keeps it on the
board: it saves the pair as the service's check (`POST /api/journeys/capture`,

change; `journeyForService` prefers a check of the service's own pack, so the
saved one is the one shown. The studio's wiring is `overviewActions`,
`overviewStartAdopt` and `overviewStartCheck` in `studio/app.mjs`: its scan,
its live job (a finished job's pack is Pack B), its file upload (a file
dropped on the page while the start is up fills the next step). The static bundle (DOWNSTREAM.md
§10) does not draw Overview: its shim answers the services and journeys
routes with 501.

**The service list** is Overview's front door where the services table
exists: one row per service and environment with its two places — the
repository (`repository` on the service record: GitHub, Azure DevOps or a
folder on the server) and the live MCP endpoint (the environment's

## What the host supplies

**`verdict-ui.mjs` reads no global state.** Its imports are the vendorable
modules above plus two one-line stubs a host can satisfy trivially:

- `escapeHtml` from `util.mjs` — any HTML escaper.
- `api` from `api.mjs` — only used as the *default* fetcher of
  `loadRunHistory(onReady, { fetchFn })`; pass your own `fetchFn(path) →
  Promise<json>` and the stub never runs.

The engines take their inputs explicitly:

```js
buildVerdictModel({ pack, packB, diff, compareBId, catalogEntry, passesLens });
projectGrade(uids, { pack, packB, diff, compareBId });
```

`pack`/`packB` are adapted layered packs, `diff` is a `/api/diff` result,
`catalogEntry` is whatever row your catalog holds for `compareBId` (only
`.label` is read). Observogram binds these from its own `state` in
`proto-synthesis.mjs` (`verdictInputs()`); a downstream studio binds them from
its own store.

**View modules never import the app shell.** The four app-level callbacks
live in `studio/host.mjs` (zero-import), filled once at boot:

```js
import { initHost } from './host.mjs';
initHost({ loadPackB, openDeployModal, renderMainView, renderTabs });
```

Views import the live object as `import { host as appHost } from './host.mjs'`
(see docs/UI_CONVENTIONS.md for the naming rule). A TypeScript host writes a
~10-line adapter object with its own implementations of those four hooks.
(The synthesis view also reuses production renderers from `compare-view.mjs`
— those are Observogram-specific; port them or swap in your own panels.)

## Contracts this repo keeps stable

- **The state-slice signatures above.** New inputs arrive as new optional
  keys, never as global reads.
- **The `initHost` hook names** (`loadPackB`, `openDeployModal`,
  `renderMainView`, `renderTabs`) — the host object never becomes a mirror
  of app.mjs (docs/UI_CONVENTIONS.md).
- **Design token and kit names.** `--og-*` properties and `.og-*` classes
  are only ever added, never renamed or removed; token names stay semantic
  (a role, not a colour word — CI rejects `--og-lime`). `design-tokens.json`
  keeps `version: 1` while that holds. Values (a hue, a radius) may change:
  that is a re-copy, not a migration.
- **Pack annotation namespace** — writers emit `observogram.*`
  (`observogram.diff.scopeMode`, `observogram.retrofeed.*`,
  `observogram.services`, `observogram.unobserved.<kind>`); readers keep
  accepting the pre-rebrand `tomograph.*` keys.
- **Diff buckets and entry fields are only ever added.** `notObserved`
  (per layer, and `summary.notObserved`) is the latest: a host whose live
  pack comes from its own fetcher gets it by writing
  `observogram.unobserved.<kind>` = reason for every artefact family that
  fetcher cannot look at (docs/DIFF.md); a host that writes none sees an
  empty array and the counts it always had. A metric family's entry adds
  `series` and `memberIds` to the artefact it embeds; a consumer that lists
  a pack's own artefacts beside the diff uses `memberIds` to give every
  series its family's status (the studio's Compare does). `declaredAhead`
  (per layer, and `summary.declaredAhead`) came after it, and those keys exist
  only when a pack carries a lifecycle statement (docs/DIFF.md).
- **`L4_SUBGROUPS`** is intentionally duplicated: `constants.mjs` owns the
  display copy, `diagnostic-grade.mjs` inlines a private copy so it stays
  zero-import. Change both or neither.
- **Env/header compat** for downstream servers proxying Observogram: every
  `OBSERVOGRAM_*` env var also honors its `TOMOGRAPH_*` spelling
  (`tools/lib/brand-env.mjs`), and the server accepts both
  `X-Observogram-Org`/`X-Observogram-CSRF` and the legacy `X-Tomograph-*`
  headers (echoing `X-Observogram-Org`).

### Sequential calls

The hook's `fetchImpl` sees every MCP request, and `OBSERVOGRAM_TRANSPORT_HOOK` loads
one module, so add the queue to the module that already prepares your gateway requests.
Two things differ from your patch. The timeout (`MCP_TIMEOUT_MS`, 30 seconds by default,
at most 300 seconds) starts when a request enters the queue, not when it reaches the
wire, so raise it to cover the wait. The transport is one per process, so the queue
serialises across every live job the server runs (up to four), not per fetch.

### Scope variables

```bash
OBSERVOGRAM_SNAPSHOT_METRIC_EXCLUDE='^demo_event_(?:\d+|blank)_total$'
OBSERVOGRAM_SNAPSHOT_FOLDER_UIDS=folder-a
OBSERVOGRAM_SNAPSHOT_RULE_GROUPS='Group One,Group Two'
```

- `METRIC_EXCLUDE` takes white-space-separated patterns, each anchored and bounded. It
  runs after `METRIC_PREFIXES`.
- `RULE_GROUPS` is a comma list, compared exactly, so a name may hold spaces.
- These values describe one team, service and environment. Keep them in the deployment's
  variables or in `OBSERVOGRAM_ORG_<KEY>_SNAPSHOT_*`, not in code (§15.2).
- The two variables your patch read inside `fetchMcp` do not exist upstream.
- After the first snapshot, read the gate log. It says whether the folder scope was pushed
  down or the rules were read whole.
- **Not built:** no tool in the capability registry takes a rule group or a folder title,
  so the rule-group and recording-rule tools your patch called were not added. Read
  `observogram.live.gaps`. If recording rules are missing, send the tool's recorded answer
  (`npm run record-fixtures -- --write`) so it can get a registry row. A hunk that calls an
  unregistered tool fails `tools/test-contract-guard.mjs`.

### Exporter manifests

Detection is by file name, so a YAML file with your keys is never read. Use
`metrics-manifest.json` (§18.1): `static_metrics` becomes `metrics`, or comes from
`packc emit --exporter`, and `dynamic_families` becomes `dynamicFamilies`.

- A pattern must be anchored and open with a literal prefix of at least three characters
  that a platform does not own (`^node_` is refused, `^node_hwmon_` is not). An entry
  that breaks a rule is a crawl warning and is not read.
- Names are tested as listed. Your patch lowercased the live name first, so check any
  pattern that relied on that.
- Members count in `jaccard` and `alignment`, and `summary.dynamicFamilies.members` says
  how many pairs rest on a pattern.
- Key on `spec.origin_kind: exporter-family`, not on the `METRIC-FAM-` id prefix.

### Lifecycle blocks

- **Move the block to the top of the file.** Only comments, `---` and Helm directives may
  sit above it. Lower down it is a warning and parks nothing.
- **Use only `deployed`, `planned` or `not-deployed` as states.** Any other word is a
  warning and parks nothing. `maturity` is optional.
- **Expect some rules to stay visible.** A symbol parks only when every file that speaks
  for it carries the same deployment, readers included. If an alert or a dashboard in a
  file with no block reads a rule, that rule still reads *declared, not live*.
- **A `PrometheusRule` custom resource is not walked.** A block in one does nothing, and a
  rule in one does not keep a series visible.
- **Update what reads the diff.** The pack carries one `observogram.lifecycle` annotation,
  not `.sources` and `.symbols`. `summary.lifecycleEnvironment` is now
  `summary.lifecycleEnvironments`, an array. Every new key exists only when a pack carries
  a statement, so read them as optional.
- **Name the environment.** `diffPacks` now takes `opts.environment`. Without it the
  statement must hold for both packs' environments, and a live pack is always bound to
  `prod`, so a staging comparison should pass `environment`.
